# 开发原则与编程要求（dsh-reasoning-level）

> 来源：用户 2026-08-23 提供（治理接入时通过 `/governance` 明确要求"给当前项目加上以下几个原则"）。
> 本文件为原则原文记录——**不翻译、不改写、不精简**；结构组织（两段 + 编号）为整理约定。
> 引用锚点：`.governance/plan-tracker.md` 项目配置「项目原则」；AGENTS.md「项目开发原则」段为每次会话自动注入。

## 开发原则

1. 分析和推演需要基于事实，不允许假设和编造
2. 实现需要进行全面的分析，避免修改遗漏
3. 实现需要考虑对原有功能的影响，避免引入新问题
4. 实现需要进行测试看护，构建防护网，避免后续问题反复
5. 实现需要考虑泛化性，严禁单点修改
6. 以高质量交付为准则，严禁为了完成任务而忽略质量
7. 修复要保证安全性，避免引入导致损坏用户数据的情况

## 编程要求

1. 设计需要考虑可扩展性和可维护性，需要基于未来进行设计
2. 实现需要避免架构腐化，避免引入架构问题和可维护性问题
3. 实现需要保证模块/类/接口的职责单一，避免引入上帝类/上帝模块和多功能接口
4. 实现不要搞任何冗余的修改，保持修改的纯粹性，一个commit承载一个问题修改/功能实现

## 执行约定（MUST）

- **每次任务执行**：任务分解、实现方案、代码审查、验收证据均须对照上列原则逐条自检（事实依据 / 影响分析 / 测试看护 / 泛化性 / 质量 / 安全）。
- **开发原则 1**：缺少事实依据（文件、命令、测试、日志、用户明确输入、外部文档）的推演与结论不得写成闭环事实——标记为 BLOCKED / 待验证 / 未知。
- **编程要求 4**：一个 commit 承载一个问题修改/功能实现；禁止顺带修改。
- **审查引用**：Code Reviewer / Test Reviewer / Design Reviewer 审查时以本文件为验收基准之一；发现违反原则的改动按 P0/P1 分级记录。
- **变更**：本文件内容变更（新增/修改/删除原则）属于项目约定变更，须经用户确认并记录 decision-log。
