# 版本演进路线图 — dsh-reasoning-level

> 决策依据：DEC-020（2026-10-20）；任务：FEAT-003
> 状态：v0.9.0 实施中；v0.10.0 / v1.0.0 为规划（触发条件写死，避免「拍脑袋排期」）

## 1. 定位再校准：这个插件真正在卖什么

插件已经解决了「配不了」的问题（v0.7.x ~ v0.8.x）：一个设置项收敛全部模型的默认思考等级、手写声明自动补齐、探测实测固化、显式选择永远优先。

但把**真实使用数据**摆在桌面上之后，价值缺口非常清楚：

| 能力层 | 现状 | 判断 |
| --- | --- | --- |
| ① 配置收敛（一个开关管所有模型） | 已解决 | 稳定，不再投入 |
| ② 能力真相（哪些档位真的可用） | **半解决**——探测能测出来，但测不出来时（`blocked`）是黑盒 | 需要「可解释」 |
| ③ 决策支持（我该用哪档？值不值？） | **基本为零** | 这是最大的未满足需求 |

**证据（本机活体 `GET /reasoning-level-stats`，81,926 次调用）**

- `zai-coding-cn/glm-5.3`：`max` × 20,084、`high` × 5、`(默认)` × 63 → 等级调节能力事实上处于「全开」状态，用户没有在做权衡。
- `deepseek-official/deepseek-flash`：`max` × 18,736、`(默认)` × 40、`off` × 1。
- 30 个模型里只有 `deepseek-official/*` 三个回报 `reasoningTokens`（总计 9.26M + 1.18M + 0.25M）；其余全部 `0` → 用户看不见思考量，也就无从判断「max 到底多想了多少」。
- `lastProbe`：`openai-codex/*` 四个模型 7 档全部 `blocked`，`persisted=skipped:no-working`；`deepseek-official/*` 四个模型实测成功但 `persisted=skipped:not-in-pi-ai-config`。→ 探测要么「测不出原因」，要么「测出来没处写」。

结论：**当前版本的瓶颈不是功能缺失，是「感觉不到」和「看不懂」。** v0.9.0 因此把重心从「能配」转向「看得懂、改得动」。

## 2. v0.9.0 —— 「看得懂 · 改得动」（实施中）

**主题**：把不可见的代价变成可见的决策依据；把需要查文档的操作变成一眼可懂的操作。

| 任务 | 承载内容 | 直接回应的痛点 |
| --- | --- | --- |
| UX-003 | 信息架构重排（页头 + 概览 KPI + 分区卡片 + 渐进披露）、等级分段控件（每档带含义与适用场景）、注入式样式体系（hover/focus-visible/响应式/动效）、表格与空态统一 | 「页面不好看」「不知道每档是什么意思」「首屏看不到自己在用什么」 |
| FEAT-004 | 模型搜索、支持矩阵、全局等级影响预览、写操作撤销、统计暂停/只看异常/排序、en 全量本地化、探测 blocked 归因、`skipped` 解释 | 「加个模型要翻长下拉」「设了不知道波及谁」「探测失败看不懂」「英文界面还是中文」 |
| FEAT-005 | 服务端 per-level 聚合（每模型每等级 calls/tokens/耗时/错误）→ 等级对比视图；思考量缺失时用思考字符近似并明示 | 「全是 max，不知道降档值不值」「一排 `—` 以为没思考」 |

**质量红线**：配置 schema / wire 语义 / 宿主契约零变更；新增字段向后兼容；7 个写入口一个不丢（RISK-005）。

## 3. v0.10.0 —— 「自动」（规划）

**触发条件**（满足任一项才启动）：
- v0.9.0 发布后 4 周内，等级对比视图有 ≥ 3 个模型覆盖 ≥ 2 个等级各 ≥ 30 次样本（说明用户真的开始按场景分化等级）；
- 或用户明确提出「不想每次手动选」。

**候选范围**

1. **场景预设（Preset）**：`快速 / 平衡 / 深度 / 攻坚` 四套映射，一键套到全局与 purpose 上（`快速` = 全局 low + compaction off + title off；`攻坚` = 全局 max）。把「7 个档位选一个」降级为「4 个场景选一个」。
   - 证据依据：活体数据里 7 档中实际只出现过 5 个（off/low/high/max/默认），`minimal`/`medium`/`xhigh` 从未被使用——7 档全铺开对用户是负担而非自由。
2. **按调用目的自动档**：把 `purposes` 从「手动两项」扩展到「可声明的规则」（如 `title/compaction` 恒 `off`，`subagent` 继承父级），并在页面上以规则卡呈现。
3. **探测归因闭环**（MAINT-018 主动探测正式立项）：对 `blocked` 的模型自动降级诊断（发最小请求判定是鉴权/模型下线/协议不支持），把「全 blocked」变成「这个模型没配置凭据」这类可行动结论。
4. **能力真值缓存**：探测结果带时间戳与来源（目录/声明/实测），页面显示「这份能力表有多少是实测的、多久前测的」。

## 4. v1.0.0 —— 「策略与治理」（规划）

**触发条件**：出现真实的多人/多设备配置共享需求，或用户明确要求成本预算约束。

**候选范围**

1. **成本策略**：为每个等级声明相对成本系数（可由等级对比视图的实测数据校准），给出「本月估算」与「预算超限降档」。
2. **配置可移植**：导出/导入策略文件（含探测产物与台账），支持在团队间共享「这套模型的推荐等级」。
3. **变更审计**：谁在什么时候把全局从 high 改成了 max（写路径已收敛在 `commit()`，加一层 append-only 记录即可）。
4. **优雅退役**：明确 v1 后的配置 schema 稳定性承诺与迁移工具。

## 5. 不做清单（明确排除，避免范围蔓延）

| 想法 | 排除理由 |
| --- | --- |
| 按任务内容自动推断等级（让模型自己决定思考多久） | 与「用户显式选择优先」的核心承诺冲突；且无可验证的判据，容易变成不可解释的黑盒 |
| 内置各厂商等级知识库并随模型更新 | DEC-012 已定案「通用词表 + 实测固定」；维护知识库是持续成本且天然过期 |
| 自定义等级名映射（用户可任意命名档位） | 宿主 wire 面只认固定 effort 值，改名只影响显示，收益低而配置面复杂 |
| 在插件内做成本计费/账单 | 需要各网关价格表，维护成本远高于价值；v1.0.0 只做「相对系数」 |

## 6. 版本与证据挂钩方式

每个版本启动前必须有一条**证据行**写进 `evidence-log`，说明触发条件已命中（例如 v0.10.0 需要「3 个模型 × 2 个等级 × 30 次样本」的实测查询结果）。没有证据不发版——避免「为了有版本而堆功能」。
